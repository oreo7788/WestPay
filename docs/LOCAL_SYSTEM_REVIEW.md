# 本地系统功能审查与待明确规则

更新：2026-10-19（Asia/Shanghai）。依据为当前本地源代码及本轮需求确认，原始审查采用静态检查；后续已完成账号权限代码改造及发布构建。本轮没有启动服务或执行测试。

## 1. 本阶段目标及已确认的业务范围

本阶段先完善本地业务系统。外部订单系统、微信实时支付、真实上游通知等连接放到后续阶段；缺少微信密钥或公网域名不再作为本地开发的阻碍。

最新身份和通道方案见 [IDENTITY_CHANNEL_MODEL.md](IDENTITY_CHANNEL_MODEL.md)。此前供应商独立登录方案已被本轮修改替代。

用户已明确：

| 编号 | 已确认的要求 | 对开发范围的影响 |
| --- | --- | --- |
| C1 | 只有内部人员和商户两类身份；超管创建用户、分配角色，控制菜单及操作按钮权限 | 超管创建商户账号并绑定商户主体，不提供自助注册或商户自行创建用户；实现角色管理、菜单/页面/操作授权及服务端数据隔离；供应商不作为登录身份 |
| C2 | 收款、付款和手续费使用统一资金余额 | 原有“预付只抵扣手续费”的实现需要重构，不能只修改字段名称 |
| C3 | 平台代收资金先进入待结算，结算确认后才可用；同时支持商户直收 | 区分直收与代收资金来源；待结算、可用和提现口径不能跨来源重复计入 |
| C4 | 客户扫码/点击链接后调起支付，成功后确认订单状态，再返回上游 | 本地先用模拟收银台、模拟结果和模拟通知记录完成闭环；真实支付与外部发送后置 |
| C5 | 需要提现及付款申请、审批、完成确认 | 付款登记表需要升级为流程单据，并与资金、处理人员和凭证关联 |
| C6 | 内部提供支持的供应商列表，商户自己填写资料；内部审核指定直收/代收模式，通过后启用 | 供应商目录、商户通道实例、配置表单、配置版本、内部指定模式、审核和启停；取消供应商独立工作台 |

“统一余额”是统一资金账户，不意味着把待结算金额直接当作可用余额。冻结资金的时点、手续费的记账时点仍待确认。

## 2. 当前本地系统已经具备什么

- 登录、退出、密码哈希；新增超管用户管理、内部/商户身份、商户主体绑定、自定义角色、多角色菜单及操作权限、停用、重置/修改密码、会话失效和服务端商户隔离。代码已构建，运行数据库尚未迁移。
- 商户、产品、通道的基础增改和启停。
- 手动创建收款订单、分页查询、详情、部分筛选、CSV 导出和模拟成功/失败。
- 金额按整数分存储；现有手续费扣减及余额流水在数据库事务中完成，部分操作具备重复请求保护。
- 首页与按商户/产品/通道统计的报表，以及预付流水。
- 通用资料登记、黑名单、操作审计和系统参数。

上述功能构成基础管理框架。现有余额、权限和付款登记尚不能满足 C1–C6 的完整业务要求。

### 确认属于页面或说明占位的部分

- “快捷登录配置”“支付相关配置”“网站信息配置”目前都进入同一通用系统参数页，没有独立快捷登录机制。
- “机器人命令”只是静态指令说明表，没有本地命令执行、群绑定或广播任务。
- “收钱吧管理”“公众号小程序”“用户标识”目前是通用资料登记，没有对应独立业务模型。
- “历史订单”按创建日期早于今天筛选，没有独立归档/结账流程。

这些页面是否进入本地首版，需要按实际使用场景取舍。不能把菜单存在视为完整功能已完成。

## 4. 可直接修复的技术缺口

以下事项不需要重新定义收付款业务，可以作为通用完善项安排：

1. 首页“按订单数量排序”的商户排行实际使用商户创建时间排序，需要修正排序与展示字段。
2. 商户的“预付”和“总预付”来自同一个累计字段，界面语义重复；统一资金模型确定后应整体调整列名和数据，而非继续保留含糊名称。
3. 预付明细查询固定最多 1,000 条，CSV 导出也沿用这一限制，缺少截断提示；需要分页导出或明确导出范围。
4. 订单 API 已支持日期、商户、通道条件，但当前订单页未完整提供这些筛选控件。
5. 账号停用、角色授权、修改/重置密码已在本轮实现；后续需要运行验收。
6. 多类记录列表没有服务端分页；日志只有最近 500 条，没有历史检索。
7. 顶部“系统运行正常”和首页支付适配器提示为固定文案，应与真实本地服务和配置状态一致。
8. 现有测试文件主要覆盖早期预付及模拟支付逻辑；新增内部/商户隔离、通道审核、结算、提现等模块开发后，需要另行安排验收覆盖。本轮未新增或执行测试。

## 5. 剩余需确认的核心规则

以下是业务决策，本文不把建议当作已批准实现。

| 编号 | 待决定事项 | 为什么会影响开发 | 建议起点（待确认） |
| --- | --- | --- | --- |
| D1 | 结算由内部财务确认、商户申请审批，还是按日自动执行？何时日切？ | 决定结算单状态、任务、权限和订单归属 | 本地首版先由内部人员按商户生成并确认批次 |
| D2 | 待结算计本金还是扣费净额？手续费在收款成功、结算还是付款时记账？ | 直接决定账户金额和重复记账规则 | 展示本金/手续费/净额明细；扣费时点统一，避免重复扣费 |
| D3 | 商户费率是否独立？通道成本是否固定，支持单笔固定费或比例分成吗？ | 决定费率配置及订单费率快照 | 先明确比例费率及商户覆盖规则，再考虑固定费和阶梯费 |
| D4 | 提现/付款何时冻结？谁审批，谁确认完成？是否禁止自己审批？ | 决定可用/冻结资金、并发申请及驳回处理 | 申请时冻结，驳回/撤销解冻，确认成功结转；申请人与审核人分离 |
| D5 | 直收与代收分别填写哪些资料，配置变更如何审核？模式已确认由内部审核指定 | 决定供应商模板、审核权限和实际收款所用凭据 | 目录与商户实例分开；审核绑定配置版本及指定模式，未审修改不能生效 |
| D6 | 是否本期支持退款/部分退款/冲正？手续费是否退还？ | 影响已结算与已提现后的资金处理 | 先定义可追溯纠错流程，禁止直接修改历史流水 |
| D7（授权方式已确认） | 用户统一由超管创建并分配角色；角色控制菜单和操作按钮权限，商户不可自行创建账号 | 需要角色管理、页面和操作权限目录，服务端鉴权及商户隔离；具体审批职责见 D1/D4 | 实施设计见 ACCESS_CONTROL.md；角色模板为建议，不自动授予现有用户 |
| D8 | 投诉会不会影响结算/提现？业务记录能否删除？ | 决定冻结与数据保留流程 | 先记录处理历史与关联，不在未确认时自动改变余额 |

其中 D1、D2、D4、D5 最优先。内部/商户入口与数据隔离、供应商目录及通道审核、独立本地模拟收银流程可以先推进设计；实际结算和资金审批逻辑要使用确认后的规则。

## 6. 建议开发顺序

### 第一批：内部/商户账号及通道开通

账号、角色权限及已有数据隔离子阶段已完成代码改造和发布构建，尚未运行验收；本批的供应商目录与通道开通流程仍待开发。

- 建立内部/商户两类身份，商户账号绑定商户主体；超管创建用户、分配角色，角色配置菜单/页面/操作权限，详见 [ACCESS_CONTROL.md](ACCESS_CONTROL.md)。
- 内部维护支持的供应商及资料要求；商户填写自己的资料，提交内部审核后启用。
- 通道实例归属商户，保存内部审核指定的直收/代收模式与审核版本，商户不能自行修改生效模式。
- 所有列表、详情、统计、导出及修改接口在后端按主体和操作权限校验。
- 补全改密、停用、会话失效和审计；不能只在前端隐藏菜单。

完成标志：相同订单在不同账号下按权限可见，商户不能通过修改 URL 越权查看、导出或修改其他商户的数据；未审配置不能启用。

### 第二批：统一资金账户及本地收款闭环

- 先确认 D2 和 D3，按直收/代收资金来源落地统一账户和原子记账服务。
- 拆分待结算、可用及必要的冻结状态，所有变动关联业务单据。
- 提供独立的本地模拟收银台和订单二维码；无需微信参数即可走完整演示流程。
- 模拟支付成功后按确定规则进入待结算，重复结果不会重复入账。
- 订单事件时间线与本地模拟上游通知记录可追溯；通知重试不能再次入账。

完成标志：本地手工建单 → 生成二维码/链接 → 模拟成功 → 待结算与订单状态一致，全程可追溯且不依赖外部机构。

### 第三批：结算、提现及付款审批

- 确认 D1 和 D4，建立结算批次及提现/付款申请。
- 落实申请、审批、驳回、撤销、完成确认，以及相应的冻结/解冻/扣减。
- 记录处理人、原因、时间与付款凭证；控制重复确认和并发操作。

完成标志：待结算不能直接提款；结算确认后可用金额正确；失败或驳回后的资金处理正确；所有单据与流水可互相追溯。

### 第四批：报表、辅助业务及运行维护

- 按已确认口径完善内部及商户报表，提供按供应商和收款模式的统计维度。
- 完成投诉关联、消息任务、日志分页、全量导出、迁移及备份恢复。
- 对不在首版本地业务范围的占位页面标明未实现或调整菜单呈现。

## 7. 当前执行边界
