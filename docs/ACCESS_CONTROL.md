# 用户、角色、菜单与操作权限方案

更新：2026-10-19。本文记录已确认需求及实施设计。本轮已实现用户/角色管理、菜单及操作授权、服务端鉴权和商户数据隔离；代码已构建，运行数据库尚未迁移，未进行运行验收。

## 已确认的要求

- 用户由超级管理员账号创建，并由超级管理员分配角色。商户不能自行注册或创建其他用户。
- 角色控制用户可以看到哪些菜单及页面。
- 页面内的操作按钮需要分别授权。
- 业务身份仍只有内部、商户两类；超级管理员属于内部身份，不新增第三类业务身份。
- 商户账号必须绑定商户主体。通道的直收/代收模式仍由获授权的内部人员审核指定。

此前“内部创建商户账号”现收敛为“由内部的超级管理员创建”。普通内部用户不因内部身份而自动具有创建用户或分配角色的权限。

## 授权模型

采用用户、角色、权限点的关联模型。建议支持一个用户分配多个同身份角色，有效权限取角色授权的并集；首版不设置用户单独授权或拒绝规则，便于解释和维护。

| 层次 | 控制内容 | 示例 |
| --- | --- | --- |
| 业务身份及数据范围 | 可操作哪类业务、哪家商户的数据 | 内部账号按授权访问平台业务；商户账号仅访问自身商户数据 |
| 页面权限 | 菜单是否显示、页面能否打开、列表及详情能否读取 | 订单列表、通道审核、结算管理 |
| 操作权限 | 页面中每个业务动作是否允许 | 创建订单、导出订单、提交通道资料、审核通道、确认结算 |

普通角色不能跨身份分配。商户角色只可配置商户适用的权限；内部审核、平台配置、跨商户数据等能力不因勾选菜单而开放给商户。

角色管理界面以“菜单/页面 → 操作权限”的树形列表配置。菜单分组本身不授予数据或操作能力；只有包含可访问页面时才显示。勾选操作时同时要求对应页面的读取权限，取消读取权限时同步清理该页面的操作权限。

权限目录由代码维护并绑定实际页面、业务动作和接口。超级管理员配置角色使用哪些已实现权限，不通过输入任意 URL 或权限名称创建新能力。新增权限默认不自动授予普通角色。

## 超级管理员与账号管理

- 超级管理员负责创建用户、设置内部/商户身份、绑定商户、分配角色、停用账号及重置密码。
- 超级管理员负责创建和维护普通角色、配置角色菜单和操作权限。
- 建议超级管理员作为受保护的系统账号标识，不作为可勾选的普通角色，普通用户不能通过修改角色或请求参数提升为超管。
- 建议保留至少一个启用的超级管理员，禁止将最后一个超管停用或降级。现有管理员账号的迁移需显式处理，不重置现有密码，不把所有旧管理员默认升级为超管。
- 角色停用、权限收回和账号停用须在后续请求生效；账号停用、密码重置使既有会话失效，不能只等客户端重新登录。
- 超管的业务操作同样遵守订单状态、配置版本和资金规则；权限不提供直接篡改历史流水或绕过审核状态机的能力。

## 页面与操作拆分示例

以下是权限目录的实施建议，不代表对应业务功能已经实现或已为现有用户授权。

| 页面 | 分别控制的操作 | 适用范围 |
| --- | --- | --- |
| 用户管理 | 创建、编辑、分配角色、停用、重置密码 | 超级管理员专属 |
| 角色管理 | 创建、编辑、设置菜单及操作权限、停用 | 超级管理员专属 |
| 商户管理 | 查看、新增、编辑、启停 | 获授权内部用户 |
| 供应商目录 | 查看；维护目录、配置资料模板、上架/下架 | 商户可查看支持目录；维护限内部 |
| 商户通道 | 查看、填写/修改资料、提交审核；审核并指定模式、启停 | 商户操作自身资料；审核和指定模式限内部 |
| 收款订单 | 查看、创建、查看二维码、主动查询状态、导出、本地模拟结果 | 按身份和商户范围；模拟操作只适用本地模拟单 |
| 资金流水 | 查看、导出；资金调整 | 商户仅看自身；调整限获授权内部人员，具体资金规则待确认 |
| 结算管理 | 查看、生成结算单、确认结算、导出 | 按身份及数据范围；生成和确认角色待业务规则确认 |
| 提现/付款 | 查看、申请、撤销、审核、完成确认 | 按身份及数据范围；审批职责分离规则待确认 |
| 系统配置及审计 | 查看配置、修改配置、查看日志、导出日志 | 获授权内部用户 |

示例权限标识可采用 `orders.view`、`orders.create`、`orders.qr.view`、`orders.query`、`orders.export`、`merchant_channels.review` 等稳定业务名称。导出、查看二维码和主动查单均不得仅复用通用“编辑”权限。

## 前后端一致执行

1. 登录态返回身份、商户归属及有效页面/操作权限，不向前端暴露密码哈希或密钥。
2. Rust 前端根据权限构建菜单、阻止无权页面入口、隐藏未授权按钮；有权限但业务状态不允许时，按钮可禁用并解释原因。
3. Go 后端对所有后台接口执行登录、身份适用范围、权限点及对象归属校验。详情、统计、二维码、导出、批量处理和修改接口都必须覆盖。
4. 商户归属从登录账号解析，不能信任请求中的 merchantId；内部用户也必须具有相应的操作权限。
5. 未登录返回 401，已登录但无权操作返回 403；越权对象查询不得泄露其他商户对象是否存在。
6. 直接访问页面、修改 URL、重放请求或直接调用接口不能绕过权限检查。公开收银台及供应商回调继续采用各自的令牌/签名鉴权，不套用后台菜单权限。
7. 权限变更使用服务端当前授权或权限版本校验，前端收到权限变更/拒绝后刷新权限；不能把登录时的旧权限永久保存在会话中继续使用。

实际允许操作须同时满足：**账号有效、身份适用、角色已授权、对象属于允许范围、业务状态允许**。

## 最小数据改造建议

- 用户：身份、商户归属、启用状态、受保护的超管标识、会话失效版本。
- 角色：名称、适用身份、启用状态。
- 用户角色关系、角色权限关系；权限目录由代码管理。
- 审计：用户创建、商户绑定变更、角色分配、角色权限前后变化、账号停用及重置密码的操作人、对象、时间、结果；不记录密码、令牌等秘密。
- 保留 `users.role` 作为旧数据兼容字段；新增 `user_access`、`access_roles`、`user_roles`、`role_permissions` 及 `access_migrations`。权限判断不再依据旧字段，旧角色显式映射到新角色及权限。

## 实施顺序与当前范围

已实现账号及角色结构、超管管理入口、后端权限校验，并接入现有菜单和业务操作。用户及角色管理仅超管可用，普通角色不能勾选这些系统管理能力。业务审批人是否可审批本人申请等细则继续按对应模块单独确认，不由角色权限的勾选隐式决定。

本轮已修改 Go/Rust 业务代码并完成发布构建，未创建或修改运行数据库中的账号，未启动服务，未执行测试或浏览器验收。

## 已实现范围及使用方式

1. 超管进入“系统设置 → 角色与权限”，创建内部或商户角色，勾选页面查看和各项操作权限。勾选操作自动补充对应查看权限；取消查看同步取消该页面操作。
2. 超管进入“系统设置 → 用户管理”，创建用户、选择身份、为商户账号绑定商户、分配同身份角色。支持编辑名称、授权、停用及重置密码。身份和商户归属创建后不可修改，以防账号沿用到其他主体。
3. 每个后台请求从数据库重新读取有效角色权限；停用账号、密码重置会删除既有会话。Rust 页面每 15 秒刷新权限，变更后刷新菜单及页面，已撤销权限立即由服务端拒绝。
4. 当前订单和历史订单分别授权；列表、详情、主动查询、二维码及导出均做服务端权限和商户归属检查。缺少二维码权限时，订单响应同时隐藏二维码地址和收款链接。
5. 首页、商户相关查询和财务报表按登录商户过滤；全局配置、资料登记、审计及用户/角色管理不开放给商户。
6. 通道启停与编辑独立授权，商户初始资金和后续调整要求资金调整权限。真实收银台及商户业务 API 继续使用原有令牌/签名/密钥认证。

商户通道实例及其开通审核尚未实现，所以当前不向商户角色开放全局通道配置或创建订单；商户可按授权查看自己的已有订单、二维码、状态及报表。权限目录只包含已存在页面与操作；供应商目录/审核、真正结算及提现审批的权限随对应业务实现再加入。商户对账当前仍是汇总报表，不代表已有结算确认。

## 首次升级与超管引导

- 下次正常启动时自动执行权限结构迁移；有旧账号时先生成 `data/west.db.before-access-随机标识.bak` 一致性备份（自定义 DB_PATH 时随该路径保存）。备份失败则终止权限迁移。原密码和业务数据保留。
- 全库只有一个旧用户且该用户为管理员时，将其认定为原始管理员并升级为受保护的超管。其他旧角色映射为普通内部角色；普通角色不具有创建用户及管理角色的权限。
- 有多个旧账号时，不自动猜测超管。可在停止服务后明确选择一个启用的旧管理员：`./bin/west-platform bootstrap-super 旧管理员账号`。该命令仅在尚无超管时可用，记录审计且不会启动服务。
- 空数据库首次初始化直接创建超管，不设置默认密码。超管标识不是普通可分配角色；当前管理页面不提供新建其他超管或降级超管的入口。
- 迁移使旧登录会话失效，需要重新登录。迁移成功后重复启动不重复生成角色或备份。
